# blaze v2

A plan, as of 2026-10-29. It lands as **one pull request** from an integration branch,
`blaze-v2`, built by parallel lanes against interfaces fixed first (section 12). It goes to main
when the whole gate, the rustc differential harnesses and the v2 performance budgets pass with
v2 as the only path (section 11). Nothing in it is a fallback to v1.

## 1. Targets

Measured on one warm VM (Graviton 5 or EPYC Turin, all cores), and on an M-series Mac for
macOS. "Edit to result" is the time from a save to a running program or a test result.

| | today (main) | v2 target |
|---|---|---|
| body edit, edit to result | ~0.29 s (nushell) | 10-30 ms |
| signature edit | ~0.31 s, 6,269 roots asked | proportional to the items whose facts changed |
| formatting or comment edit | recompiles the file's functions' places | compiles nothing |
| rename or move of an item | recompiles dependents | compiles nothing |
| no-op build | 11 ms (ripgrep) | under 5 ms |
| daemon start, warm | 35 s (nushell); up to 238 s in CI | under 1 s (mmap the image) |
| blaze's own CI, small PR | 30 min+ | under 2 min, the changed code and the tests it reaches |
| cold build of blaze | ~12 min of mostly serial codegen | bounded by the critical path, all cores busy |
| memory | runners OOM; cold ripgrep 2.0 GB live vs cargo's 0.56 GB (#806); nushell 12.5 GB (#734) | never OOM: admission against a budget; peak at most cargo's |
| body edit of a big top crate | ruff 75 s, ty 147 s; cargo 7 s; Astral's fork 0.3 s (#1450) | under 50 ms |
| dev-build code speed | ripgrep's dev build runs 5.8x slower than cargo's debug build (#1404) | at least as fast as cargo's debug build |

Non-goals: changing what Rust means (superset-of-rust holds); running rustc for anything
(no-rustc holds); a fallback when v2 can't do something (no-fallback holds: it stops and says
what and where); an IDE. The only interface is the agent API (CBOR over a socket or HTTP),
shaped for LLMs; the IDE crates (`ide-db`, `hir-ide`, `ide-diagnostics` and the rest) are not
a constraint, and what the compiler needs from them (diagnostics) moves into the compiler.

**Everything is ours.** Any dependency v2 needs to change is in the workspace and changed in
place: salsa (`vendor/salsa`), cranelift, llvm-sys, `rustc_type_ir` and the trait solver are
already there; anything else is vendored the moment it's in the way.

**Deterministic**: the same inputs give the same bytes, whatever the scheduling, the core count
or the machine. The invalidation oracle (section 11) depends on it.

**Profile first**: before the targets bind, the coordinator measures where today's 0.27 s body
edit and 35 s start go, and the targets are set from that.

## 2. The machine model

- **One warm VM per project** (or per tenant's projects), all its cores, effectively unlimited
  local disk. One blaze daemon holds one query database and one store.
- **A branch, a PR or a CI job is a view**: a root of the Merkle VFS (a map of every file to its
  content hash). Opening a view is constant time; building it computes only what its inputs
  reach that no other view already computed.
- **Results are keyed by the hashes of their inputs, never by view or revision**, so every view
  shares every equal result. Identical work in flight runs once (single-flight).
- **Forks of the VM only for**: another tenant (isolation), a build bigger than one box (helpers
  for a slice of codegen), and snapshots to resume after a crash or a stop.
- **macOS and Windows** each get their own warm machine running the same daemon.

## 3. Sans-IO core and drivers

From blaze-next's `blaze-core` and the `sansio` lane's steps 1-3 of `docs/driver.md`
(on main), finished:

- The compiler core is pure: it takes completions, returns effects (read, write, sync, spawn,
  watch, timer). No thread, file, socket or clock in it.
- **Drivers**:
  - Linux: io_uring (reads, writes, fsync, timers, accept and recv for the API, linked
    submissions), fanotify for file changes, `pidfd` for children, Landlock + seccomp +
    namespaces for sandboxes.
  - macOS: kqueue, FSEvents, `clonefile`, `F_FULLFSYNC`, Seatbelt for sandboxes.
  - Simulation: a seeded virtual clock, shuffled completions, injected failures, torn writes,
    power cuts. Every test of the core runs here over many seeds.
- Steps 4-7 of `docs/driver.md` (workspace load, codegen overlapping store writes, link and
  tests, inputs committed while work runs) are part of v2.

## 4. Scheduler and memory

- **One worker thread per core**, work stealing, steal order by topology: same CCD (EPYC) or
  cluster (Graviton, Apple P/E) first, then the same socket, then any.
- **The task is a query execution**, found dynamically. A task that needs another query's
  result reuses it, waits on it if it's running, or runs it inline.
- **Priority**: interactive requests over background CI; within a request, the critical path
  first (signatures and anything many tasks wait on before leaf codegen). Each request gets a
  fair share of the cores.
- **Memory-budget admission**: every task runs in its own bump arena, so its memory is
  measured; the scheduler keeps an estimate per query kind (learned, persisted) and admits work
  only while the estimates fit the budget (the VM's memory minus a margin).   A task over its
  estimate is let finish; the estimate grows. Never OOM, never a silent slowdown: a request that
  can't fit at all is refused with what it needed.
- **Hard backstop**, because estimates can be wrong: every sandboxed process has a memory limit
  (cgroup on Linux, a resource limit on macOS); the daemon caps its own arenas and spills cold
  results to disk before it reaches its limit; a task that would pass the cap waits.
- **No lock on the hot path**: sharded interners and memo tables, results immutable once
  written, readers never lock.

## 5. Data formats

One rule: **the bytes in memory are the bytes on disk.** Every long-lived structure is
pointer-free, aligned and position-independent, so it can be mmapped and used in place.

- **IDs, two kinds**: a dense `u32` index per arena for speed, and a content hash for identity.
  Dense indices are assigned in arrival order by parallel workers, so they differ between runs
  and never appear in a hash, a key or the bytes of an output; hashes, keys and outputs use
  content IDs only, and each arena maps one to the other. No `Arc` in long-lived data. Interned
  values (symbols, types, paths) sit in sharded, append-only interners keyed by content hash.
- **Syntax**: one flat tree per file everywhere (no rowan, no IDE to keep): tokens as (kind,
  length) with text read from the mmapped source; nodes in preorder as (kind, subtree size);
  parents and offsets by arithmetic. About 8-12 bytes a node instead of ~40 and an allocation.
  An edit reparses the changed item into a new flat tree. Builds on #42 (flat-syntax).
- **Schema**: every on-disk structure has a versioned schema hash. The image and packs are
  keyed by it, so a blaze build that changes a layout reads nothing it can't read; it rebuilds
  the image from the store's results (fast, section 7) instead of from source.
- **HIR, bodies, MIR**: struct of arrays (kinds, types, spans in their own columns), `u32`
  indices.
- **Spans** in a side table relative to their anchor, out of every hash; a formatting edit
  changes the side table only.
- **Machine code**: each function a relocatable blob with its relocation list, keyed by its code
  hash; debug info and panic locations in a side table, keyed by the same hash.

## 6. Minimal invalidation (Unison, and finer)

Unison's idea: a definition is its content hash; names are metadata pointing at hashes. A
rename or move changes no hash, and a change to one definition is a new hash that dependents
refer to only if they're updated. Rust's semantics need dependents updated when meaning changes,
so v2 takes Unison's identity and adds facts that say exactly when meaning changed.

### 6.1 Items by content

From blaze-next's `blaze-items` (#344), made the key of everything:

- Each fn, type, trait, impl, const, static and macro hashed in normalized form: after
  expansion, resolution and inference, with no names, spans or order, references as hashes of
  what they refer to, cycles as Unison's (a cycle hashed as one unit, members by position).
- Four hashes per item:
  - **interface**: what a user of it can see (a fn's signature and bounds; a type's fields,
    variants and generics; a trait's items);
  - **layout**: size, alignment, field offsets, niche, ABI (types only);
  - **code**: the normalized MIR body;
  - **deep**: the code with every callee's code hash, for what inlines.
- A name, a module path, a file and a position are **not** in any hash unless the program can
  observe them. Rename, move and reformat change nothing the compiler reads, except:
  - **names are observable** through `type_name`, `module_path!`, symbol names (mangling),
    `#[no_mangle]`, `#[export_name]` and `#[link_name]`; a query that reads a name records the
    fact "the name of X" and reruns when it changes;
  - **positions are observable** through `line!()`, `column!()`, `file!()` and
    `#[track_caller]`'s `Location`; these become references into the span side table, filled
    at link time, so a reformat patches values without compiling.
- **What a body leaks into its interface** is part of the interface hash:
  - the hidden type of an `impl Trait` return and of an `async fn`'s future, and whether it is
    `Send`, `Sync`, `Unpin` (auto traits leak through opaque types);
  - a `const fn`'s body, for the constants that evaluate it;
  - a closure's inferred signature and captures, for its users.
- **Layout is deep**: a type's layout hash covers its fields' layouts, niches, `repr` and the
  target, transitively.

### 6.2 Dependencies on facts, not items

A query records the narrowest fact it read, not the item it read it from:

| fact | read by | invalidated when |
|---|---|---|
| signature of fn F | callers' type checking | F's interface hash changes |
| layout of type T | codegen of everything that moves or stores a T | T's layout hash changes, not its methods or docs |
| field f of T: its type and offset | field accesses | that field changes, not the others |
| method resolution of `x.m()` on type T | the caller | an impl or trait adds, removes or changes an `m` reachable for T |
| does T implement Trait | trait solving | an impl of Trait whose simplified self type unifies with T is added, removed or changed |
| name N in scope S resolves to X | name resolution | an item named N appears or disappears in a scope S sees (including through globs) |
| code of F | codegen of F; callers that inlined F (release) | F's code hash changes |
| a const's value | its users | the evaluated value changes, not its expression |

Rules that reach across items get facts of their own, each with edit kinds in the fuzzer
(section 11) aimed at it: coherence and orphan checks, specialization, inference fallback, drop
check, vtable layout, derives, glob imports and shadowing, macro hygiene, auto-trait leakage.

Negative facts ("no impl of Trait for T", "N is not in S") are kept in indexes keyed by
(trait, simplified self type) and (scope, name), so adding an impl or an item touches only the
queries that asked a question it now answers differently.

Early cutoff at every level: each result stores a 128-bit fingerprint. A rerun that produces
the same fingerprint stops there. Fingerprints stay when values are evicted (section 7), so
eviction never breaks cutoff.

### 6.3 Per edit, what reruns

| edit | reruns |
|---|---|
| formatting, comments, whitespace | the span side table of the file and the positions it fills; no code |
| rename or move of an item | the name index, and only queries that read the name (section 6.1); no code otherwise |
| body of F (dev) | F's inference, MIR, codegen; F's blob patched in place; callers too only if F's body leaks into its interface (opaque type, auto traits, `const fn`) and that changed |
| body of F (release) | the same, plus callers whose deep hash includes F |
| signature of F | callers whose resolved call depends on what changed |
| a private field of T | users of that field; codegen of users of T's layout if it changed |
| an impl added | queries whose (trait, self type) or method lookups it now answers |
| a generic fn's body | its instances that are still reached, by their (code hash, type-argument facts) |
| Cargo.toml features | the crates whose cfg set changed, at item granularity |

### 6.4 Monomorphization and sharing

- An instance is keyed by (generic's code hash, the facts of its type arguments it reads), so
  identical instances across crates, branches and projects are compiled once.
- Identical normalized MIR anywhere is one compiled function (code dedupe).

### 6.5 Build scripts, proc macros, tests

- **Traced inputs**: the sandbox records every file, directory listing and environment
  variable a build script or proc macro reads. Its result is keyed by exactly those (plus its own
  code hash), not by "the package changed".
- **Proc macros**: expansion keyed by (macro's code hash, input tokens, traced inputs);
  wasm proc macros where the crate allows, native in the sandbox otherwise.
- **Tests**: each test's reached functions (by code hash) are recorded; a change reruns only
  tests that reach a changed hash.

## 7. The query database

- **Our own query database.** It starts from `vendor/salsa`, already in the workspace, and is
  remade into blaze's: red-green queries keyed by input hashes (section 2), not by revision;
  fingerprints on every edge; results in the zero-copy format; many views at once;
  admission-aware execution. It is no longer a vendored copy kept close to upstream.
- **Why did this rerun**: the agent API answers, for any query that ran, the chain of facts
  back to the input that changed. Over-invalidation is debugged with it, and the oracle reports
  through it.
- **The LRU caps go away as a correctness problem**: today `parse` (128), `macro_expand` (512),
  `ast_id_map` (1024) and others evict values, and salsa can only backdate by comparing values,
  so every evicted result counts as changed and its dependents rerun (`INCREMENTAL.md`: every
  macro of a file expanded again on each edit). v2 keeps a fingerprint with every dependency
  edge, as rustc does; values can be evicted to disk and cutoff still works.
- **Signature and body queries split**, so dependents start when signatures are known.
- **Parallel macro expansion**: each round of the resolve-and-expand fixpoint expands every
  resolvable invocation in parallel; macros inside bodies expand with their function's task.
- **Garbage collection by reachability** from live views and kept roots; cold results move to
  disk, nothing is deleted while reachable.
- **The daemon image**: the whole database written as one zero-copy image (section 5); a start
  is an mmap and pages on demand.

## 8. Store

- One content-addressed store on the VM's disk, keyed by BLAKE3 of exact inputs (source,
  cfg, features, target, toolchain, the layout facts read). A key that misses an input is a bug.
- **Packs**: aligned zero-copy records, mmapped. Hot objects uncompressed; cold objects zstd
  with a dictionary per kind. Large outputs content-defined-chunked, so near-identical binaries
  across views share bytes. Outputs placed with reflink (Linux) or `clonefile` (macOS).
- **Index**: an mmapped open-addressed table on BLAKE3 keys; one or two cache misses a lookup.
- **Verified**: a read checks the content hash; archive and path entries can't escape their
  directory.
- **Remote** is a read-through tier for machines outside the pool (a laptop) only, never on the
  hot path of the VM. Supersedes the per-job, per-pin remote naming (#1481).

## 9. Codegen and linking

- **Per-function codegen units**: the unit of codegen is a function, not a crate. The
  `blaze_engine` tail (one 12,000-line crate compiling alone at the end) disappears.
- Dev: Cranelift per function. Release: LLVM per function with ThinLTO-style summaries, inlining
  recorded as deep-hash edges (section 6.1). Release code must run as fast as rustc's: the
  summaries carry what cross-function passes need (inlining, constant propagation through
  arguments, dead-argument removal, devirtualization), and a release benchmark against rustc's
  output is one of the budgets.
- Code dedupe never merges statics or anything whose address the program can compare as
  distinct.
- **Linker**: parallel and in place. Changed functions are placed in per-thread chunks of
  address space and written independently; relocations are applied in parallel; callers of a
  moved function go through a jump table (one slot changes) or are patched in parallel; the
  symbol table is a sharded map. The only serial step is the commit: one atomic switch that
  makes the new image visible, so nothing runs a half-patched binary. Full links are parallel
  the same way.
- Live patching (blaze-live) uses the same blobs and commit.

## 10. CI on the VM

- The project's warm VM **is** the CI. A webhook for a push or PR opens a view on the running
  daemon and builds its diff: no runners, no cache transfer, no workspace load.
- Results go back to GitHub as check runs, so required checks and `land.py` keep working.
- **Release train**: one at a time on the VM; a newer tag replaces the waiting one (latest wins).
- macOS and Windows checks from their own warm machines, the same way.
- Fork PRs run on the shared machine, so every build script, proc macro and test runs in a
  per-process sandbox and no secret is readable inside one.
- **Only the daemon writes the store.** User code's outputs are hashed and checked by the
  daemon before they're stored, so a sandbox escape can't poison what other views read. Each
  tenant has its own store; only the read-only base layer of public dependencies is shared.
- **One shared memo table means one wrong result is wrong everywhere**, so the VM runs the
  invalidation oracle continuously in production: it rebuilds sampled views from scratch and
  compares them; a mismatch stops the affected results and names the fact that missed.
- **No single point of failure**: the VM snapshots itself, and a standby resumes from the
  newest snapshot.
- First step: one persistent ix VM where each Actions job only sends a request to the warm
  daemon (the ix-runners App can place jobs there). Then the VM posts check runs itself and
  Actions is dropped for these checks.

## 11. Proving it

Testing happens **all at once, on the integrated branch**, not per lane. Lanes write their
code and the tests for it, and keep `blaze-v2` building; they don't run suites. The coordinator
and `v2-proof` run everything together once the lanes' work is in:

- **Differential against rustc** (`harness/toolchain` nightly): the existing harnesses, plus a
  corpus of real crates (top crates.io, blaze, nushell, ripgrep, helix) built and run both ways,
  outputs and test results compared.
- **Invalidation oracle**: for random edit sequences (fuzzed: body, signature, impl, rename,
  move, format, cfg, feature), the incremental result must equal a from-scratch build of the same
  sources, bit for bit for the codegen inputs. Over-invalidation is measured and budgeted;
  under-invalidation is a failure.
- **Rejections**: rustc's compile-fail tests must fail under blaze with the same error codes (#1522, #1440).
- **Simulation** of the core and the store over many seeds (crashes, torn writes, reordered
  completions); the daemon image and journal must recover.
- **Memory**: builds under a tight budget must finish, slower, never OOM.
- **Performance budgets** (section 1) as required checks, measured on the VM, including release
  code speed against rustc's.
- **Determinism**: every corpus build twice, on different core counts, byte-identical.
- **Platforms**: Linux (x86-64, aarch64), macOS (aarch64), Windows (x86-64, MSVC), wasm, and
  cross-compilation; debuggers (gdb, lldb) reading the debug-info side tables.

## 12. How it is built: lanes on one integration branch

Each lane is a cursor-agent (`--yolo`, Opus 5.5 medium) in its own worktree, on a branch off
`blaze-v2`, merging into `blaze-v2` with `--no-ff` when its code builds. The coordinator fixes
the interfaces first (step 0 below) and owns them afterwards: a lane that needs an interface
changed asks the coordinator, who changes it on `blaze-v2` for every lane at once.

**Main is frozen** for the crates v2 rewrites while v2 is built: bug fixes only, each one
merged into `blaze-v2` by the coordinator the same day. Other crates keep landing on main as
usual and are merged in daily.

| lane | owns | depends on |
|---|---|---|
| `v2` (coordinator) | the profile of today, the interfaces, the branch, main merges, the full suite, the final PR | — |
| `v2-core` | sans-IO core, drivers (io_uring, kqueue, simulation), scheduler, admission | interfaces |
| `v2-vfs` | Merkle VFS, views, journal, file watching | core |
| `v2-format` | the zero-copy format and schemas, both kinds of IDs, sharded interners, flat syntax (replacing rowan), SoA HIR, span side tables | interfaces |
| `v2-db` | our own query database from `vendor/salsa`: input-hash keys, fingerprints, views, signature/body split, GC, daemon image, parallel expansion, the rerun explainer | format |
| `v2-items` | item hashes (interface, layout, code, deep), facts, negative-fact indexes, rename and move | db |
| `v2-store` | packs, index, compression, chunking, verification, remote tier | format, core |
| `v2-codegen` | per-function units, instance keys, code dedupe, release inlining edges | items, store |
| `v2-link` | the parallel in-place linker and commit, debug side table, live patching | codegen |
| `v2-usercode` | traced-input sandboxes for build scripts and proc macros, wasm proc macros, warm process pool, test selection | core, store |
| `v2-ci` | the VM as CI: webhook, views per PR, check runs, the train | vfs, db |
| `v2-proof` | the invalidation oracle and fuzzer, the crate corpus differential, performance budgets | all, from day one against v1 |

Order:

0. **Interfaces** (coordinator, first): the effect and completion types, the task and admission
   API, the ID and arena types, the query key and fingerprint types, the item-hash and fact
   types, the store's get/put API. Written as crates with types and doc comments and no logic,
   merged into `blaze-v2` before any lane starts.
1. All lanes in parallel against the interfaces, writing code and its tests, keeping the
   branch building, running no suites.
2. `v2-proof` builds the oracle, the fuzzer, the corpus and the budgets in parallel, and sets
   the bar by running them against v1.
3. Integration, all at once: everything is run together on `blaze-v2`; failures go back to
   the owning lane; v1's paths are deleted and the IDE crates v2 doesn't need are removed; the
   branch is green on the whole gate with no v1 path left.
4. One PR to main through `land.py`; the docs this supersedes (`driver.md`, `INCREMENTAL.md`'s
   plan parts, `remote-cache.md`, `linker.md`) marked or rewritten in the same PR.

## 13. From the issue tracker

Open issues that v2 takes in (or closes by design), by the lane that owns each. A lane reads
its issues before starting; v2's PR closes the ones it resolves.

**Lessons that change the design**
- **#1450**: ruff's 75 s body edit is one function recompiled plus 35 s of build scripts rerun,
  because a build script with no `rerun-if` directive reruns on any change to its package
  (cargo's rule). Traced inputs (section 6.5) fix it at the root: a script reruns only when
  something it read changed. A script that reads what can't be traced (the clock, randomness,
  the network) keeps cargo's rule. (`v2-usercode`)
- **#906**: a stale sibling closure after a capture change gives silent wrong results. Closure
  captures are a fact of their own (section 6.1), and this repro goes into the oracle's corpus.
  (`v2-items`, `v2-proof`)
- **#350**: backdating across a durability drop was unsound in blaze-next and broke 49 of 71
  splices. Our own query database (section 7) verifies inputs soundly: no backdating unless the
  fingerprint and every input are equal. (`v2-db`)
- **#1439**: the store keys every value by a hash of all of blaze's sources, so any release
  turns CI cold. v2 keys a value by the schema and code of what produced it (section 5,
  Schema). (`v2-store`)
- **#1522, #1440**: blaze accepts code rustc rejects. The differential corpus compares
  rejections too: every compile-fail test of rustc's suite must fail under blaze with the same
  error code. (`v2-proof`)
- **#686**: every process indexes the whole store (1.6-1.8 GB each, OOM at 117 GB). In v2 only
  the daemon holds the store, and its index is the mmapped table. (`v2-store`)
- **#806, #734**: memory goes to compiled code kept after it's in the store (23%), the MIR of
  every compiled body (15%), and parses of every dependency body kept for `declared_in` (10%).
  v2 moves results to disk once stored, and parses dependency bodies only on demand (below).
  (`v2-db`, `v2-format`)
- **#1325, #1326, #805**: deleted `include_str!` inputs not invalidated, literal whitespace
  changing fingerprints, a worker keyed by `PATH`. Each becomes an oracle edit kind, and the
  environment becomes a traced input, not part of a worker's identity. (`v2-proof`, `v2-usercode`)
- **#1480**: two store inputs not hashed (unreadable sources skipped, the C compiler of build
  scripts). Traced inputs hash both. (`v2-usercode`, `v2-store`)

**Optimizations to build in** (most from makepad's Relax compiler, #1290)
- **#1293 demand-driven front end** and **#1294 outline parse**: dependency crates are parsed
  as item outlines (4-byte packed tokens), and their bodies are parsed, lowered and inferred
  only when codegen reaches them. `blaze check` still checks the workspace's crates fully.
  (`v2-format`, `v2-db`)
- **#1291 back-end memo**: instances equal up to callee renaming compile once (anim: 7,587 fns
  plus 70,330 instances). Keyed exactly: constants, layout facts and symbols stay in the key.
  **#1292**: functions that differ only in constants fold into one with the constants as
  parameters (dev builds; release only if run time holds). (`v2-codegen`)
- **#1336**: per-function keys across revisions; Astral's version gained within noise on narrow
  function classes. v2's item hashes generalize it; measure on their benchmark. (`v2-codegen`)
- **#1295 front-end images** and **#1299 settle rebuild**: after a cold build, the daemon writes
  its image and swaps to the mapped warm state, dropping the cold arenas (anim's worker sat at
  6 GB). (`v2-db`)
- **#1298 store as one mapped file per crate version**: append payloads, write the index into
  the inactive of two slots, flip the header; one barrier, not a sync per entry (anim cold
  wrote 77,481 entries serially). (`v2-store`)
- **#1296 build-script elision**: scripts that are provably only constant `println!`s of cargo
  directives are evaluated without compiling or running them, checked against running them.
  **#804**: build scripts are compiled by the daemon, not by fresh processes reloading the
  sysroot (2 s each). (`v2-usercode`)
- **#1297 native expanders** for the macros every graph uses (serde_derive, thiserror,
  bitflags, tokio): used only when the macro's source matches the verified copy byte for byte,
  otherwise the normal expansion runs (an exact-match cache, not a fallback); a verify mode runs
  both and compares tokens and spans. (`v2-usercode`)
- **#1301 owner thread with pump-wait**: the rule for any wait inside a step: a waiting
  thread serves requests, and a nested request that needs what an outer one holds is cancelled
  and reposted, so no deadlock by construction. (`v2-core`)
- **#1443 a process per test from a fork server**: each test binary starts once in its sandbox,
  forks a copy-on-write child per test (0.1-0.5 ms on Linux), one global queue over all cores.
  **#227, #1330**: run only the tests an edit reached. (`v2-usercode`)
- **#1404, #635**: dev code speed. Find where blaze's dev ripgrep loses 5.8x (stack frames,
  #1307's smaller Cranelift frames, overflow checks, missed inlining, calls through patch
  slots) and fix it in codegen; tests built at the profile's opt-level. **#807**: tiering,

## 14. Risks

- **One huge PR**: review and merge conflicts with main. Mitigation: main merged into
  `blaze-v2` daily by the coordinator; the PR's review is the test suite plus the per-lane design
  notes, not a line-by-line read.
- **Facts too fine**: tracking costs more than it saves. Mitigation: the oracle measures both
  under- and over-invalidation; any fact kind can be coarsened without changing correctness.
- **ix VMs that don't place or stay up**: the `sansio` lane couldn't measure on 16 cores. A lane
  without a VM says so in its HANDOFF and stops on measurement, never runs on the Mac or AWS.
- **Front-end churn**: `hir-*` changes (IDs, SoA, fingerprints) touch the most code. They keep
  rustc's semantics; the differential corpus is the check.
- **Testing all at once**: the first full run will fail in many places together, and failures
  that cross lanes take longest. Mitigation: the oracle and corpus exist before integration
  (step 2), so failures come with the fact or crate that broke, and the explainer says why.
- **A chain of lanes** (format, then db, then items, then codegen, then link): downstream lanes
  build against the interfaces and their own stubs, not against finished upstream work.
- **Toolchain bumps get cheaper, not costlier**: with item hashes, a new nightly's std
  invalidates only the std items that changed.
